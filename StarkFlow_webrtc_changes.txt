1. ПЛАГИН (plugin/c3runtime/instance.js)
----------------------------------------------------------------------

1.1. Включение. Сервер пишет в welcome "rtc": true и "iceServers": [...].
     Плагин пробует WebRTC, только если в welcome есть И rtc: true, И sync: true.
     Старт — сразу после welcome, не ждём входа в комнату: пока игра
     раскачивается, ICE успевает подняться.

1.2. Сигналинг — по уже открытому WebSocket:
       клиент -> {"t":"rtc.offer","sdp":"..."}
       сервер -> {"t":"rtc.answer","sdp":"..."}
       обе стороны -> {"t":"rtc.ice","candidate":{...}}   (trickle ICE)
       обе стороны -> {"t":"rtc.close"}   ("эту сторону закрыли")
     Оффер всегда делает клиент, сервер только отвечает. ICE-кандидаты
     сервера, пришедшие раньше rtc.answer, плагин придерживает и добавляет
     после ответа (иначе браузер их отвергает).

1.3. Канал: один DataChannel "sync", ordered: false, maxRetransmits: 0
     (честный "отправил и забыл"). В нём те же JSON {"t":"sync",...}, что и по
     WebSocket. (В плане было "без обёртки t:sync" — оставил обёртку: это
     ~11 байт, зато сервер разбирает снимок тем же кодом.) Из канала плагин
     принимает только sync, остальное игнорирует.

1.4. Отправка снимка (_flushSyncChannel): канал открыт — снимок уходит в
     DataChannel мимо WS-очереди, иначе как раньше в WS-батч. Двойной отправки
     нет. Снимок всё равно идёт по WebSocket, если канал не открыт, забит
     (больше 64 КБ в очереди), снимок больше maxMessageSize, или это ПУСТОЙ
     снимок objs: [] (см. 3.2).

1.5. Откат на WebSocket:
     - канал не открылся за 3 с -> rtc.close, до перезагрузки страницы WebRTC
       больше не пробуется;
     - канал упал посреди игры -> rtc.close, sync сразу идёт по WS, при
       следующем реконнекте попытка будет снова;
     - нет RTCPeerConnection (worker-режим Construct, старый браузер) -> одна
       строка в лог, остаёмся на WS;
     - ошибка в offer / плохой answer -> rtc.close, остаёмся на WS.

1.6. Уборка: соединение закрывается при закрытии сокета, обрыве, disconnect,
     повторном welcome и при rtc.close от сервера.

1.7. Новое в коде: методы _sendUnreliable, _rtcStart, _rtcStop, _onRtcAnswer,
     _onRtcIce, _onRtcMessage; поля _rtcPc, _rtcDc, _rtcTimer, _rtcRemote,
     _rtcIce, _rtcMaxMsg, _rtcGaveUp, _rtcWarned; константы RTC_TIMEOUT,
     RTC_BUFFERED_MAX, RTC_ICE, STALE_SEQ, STALE_MS; case "rtc.answer",
     "rtc.ice", "rtc.close" в _dispatch.

2. СЕРВЕР
----------------------------------------------------------------------

2.1. server/internal/rtc/rtc.go (новый пакет, pion/webrtc v4).
     - Один UDP-порт на ВСЕХ клиентов (ICE UDP mux) — на хостинге открыть
       один порт проще, чем диапазон.
     - STARKFLOW_RTC_PUBLIC_IP подставляется в ICE-кандидаты (NAT 1:1): без
       него в Docker сервер предложил бы клиенту внутренний адрес контейнера.
     - Только UDP4. Максимальный размер сообщения — 64 КБ (объявляется в
       answer, плагин по нему меряет свои снимки).
     - Принимается только канал "sync" и только неупорядоченный, один на
       соединение; любой другой канал сразу закрывается.
     - Канал, не открывшийся за 15 с, закрывается (плагин сдаётся за 3 с, это
       только освобождает серверную сторону).
     - Peer.Send: отправка только если канал открыт и не забит (64 КБ);
       иначе false — и комната шлёт снимок по WebSocket.

2.2. server/internal/server/client.go.
     - welcome: "rtc": true и "iceServers" — только если движок запущен.
     - rtc.offer -> rtc.answer; ICE-кандидаты в обе стороны; rtc.close.
       Ограничения: offer до 16 КБ; не больше 4 offer на одно соединение
       (иначе ошибка 500) — чтобы нельзя было наплодить сотни
       PeerConnection; при новом offer старый канал закрывается.
     - Снимки из канала: только "sync", свой лимит частоты на канал (тот же
       60/с, что и для WS), лишнее молча отбрасывается. Дальше — тот же
       Room.Sync, что и для WebSocket: все проверки и лимиты (401/404/500)
       те же, ошибки уходят по WebSocket.
     - Канал упал на стороне сервера -> клиенту уходит rtc.close.
     - Канал закрывается при закрытии WebSocket.
     - Снимки из канала приходят в другой горутине (не в readPump), поэтому
       комната для неё хранится в атомарном указателе (setRoom — единственное
       место, где она меняется). Гонок с readPump нет.

2.3. server/internal/room/room.go.
     - Новый необязательный интерфейс UnreliableConn (SendUnreliable). Conn не
       менялся, старые реализации и тесты не затронуты.
     - Room.Sync рассылает каждому получателю ОДНИМ путём: в его открытый
       WebRTC-канал, иначе в WS-батч. Пустой objs: [] — всегда по WebSocket.
     - Отброс опоздавших снимков (см. 3.1): снимок с seq не больше последнего
       принятого от этого игрока не пересылается и не сохраняется. Счётчик
       сбрасывается при возврате игрока (resume после перезагрузки страницы
       начинает seq с 1). Снимок без seq (0) принимается всегда — для
       совместимости со старыми клиентами.

2.4. Новые переменные окружения:
     STARKFLOW_RTC_PORT       — UDP-порт; не задан = WebRTC выключен.
     STARKFLOW_RTC_PUBLIC_IP  — внешний IP (через запятую); обязателен в
                                Docker и за NAT.
     STARKFLOW_RTC_ICE        — STUN для клиентов, по умолчанию
                                stun:stun.l.google.com:19302; none — пусто.
     Если UDP-порт занят или не открылся — в лог ошибка, сервер работает
     дальше без WebRTC (не падает).

3. ПРОБЛЕМЫ, КОТОРЫХ НЕ БЫЛО В ПЛАНЕ (найдены и закрыты)
----------------------------------------------------------------------

3.1. Пакеты не по порядку ломали интерполяцию.
     Раньше плагин при seq <= последнего считал, что отправитель начал
     заново, и СБРАСЫВАЛ буфер снимков. По TCP это верно, по UDP — нет:
     каждый опоздавший пакет обнулял бы буфер, и объекты дёргались бы СИЛЬНЕЕ,
     чем сейчас. Теперь плагин отбрасывает опоздавший снимок (seq в пределах
     64 и ts в пределах 2 с назад от новейшего), а снимок с меньшим seq, но
     более поздним ts по-прежнему считает перезапуском. Сервер тоже
     отбрасывает опоздавшие (2.3).

3.2. Потеря пустого снимка = призраки.
     Пустой objs: [] означает "моих объектов больше нет". Если бы он ушёл по
     UDP и потерялся, у других игроков навсегда остались бы копии объектов.
     Поэтому и плагин, и сервер шлют его только по WebSocket. А сервер не даёт
     опоздавшему непустому снимку "оживить" объекты после пустого.

4. ЧТО НАДО ЗНАТЬ ПРИ ДЕПЛОЕ
----------------------------------------------------------------------

4.1. Go 1.24. pion тянет golang.org/x/net, которому нужен Go 1.24, поэтому в
     go.mod теперь go 1.24.0, а в Dockerfile образ сборки golang:1.24-alpine.
     (1.22 к тому же давно без обновлений безопасности.) Локально собирать
     тоже Go 1.24+.

4.2. UDP. Нужен открытый UDP-порт STARKFLOW_RTC_PORT (в Docker пробросить
     "40000:40000/udp" — строка закомментирована в docker-compose.yml) и
     STARKFLOW_RTC_PUBLIC_IP. Туннель Cloudflare и типичные хостинги ботов
     (Bothost?) UDP не пропускают — проверить у поддержки. Если UDP не
     доходит, ничего не ломается: плагин через 3 с остаётся на WebSocket.
     Работает ли канал — строка "[StarkFlow] sync goes over WebRTC" в
     консоли браузера, подробности в chrome://webrtc-internals.

4.3. Worker-режим Construct. В воркере нет RTCPeerConnection — плагин там
     останется на WebSocket. Если в проекте "Use worker" = Auto/Yes, WebRTC
     работать не будет. Обход — через DOM-side скрипт плагина, отдельная
     задача.

4.4. Версию аддона (addon.json) не поднимал — поднять при сборке .c3addon.
