# Деплой StarkFlow

Сервер — это один Go-бинарник в Docker-контейнере: слушает `0.0.0.0`, состояние нигде не хранит,
ему хватает 64–128 МБ памяти. На сервере нужен только Docker, больше ничего ставить и настраивать не надо.

## Какой вариант выбрать

| Вариант | Когда подходит | Что понадобится |
|---|---|---|
| [Установщик](#установщик-один-скрипт) | чистый VPS, хочется без ручной правки конфигов | Ubuntu/Debian, один скрипт |
| [Свой ПК + туннель](#публичный-сервер-прямо-со-своего-пк-windows-без-docker) | поиграть с друзьями сегодня, без VPS и Docker | Windows, один скрипт, Cloudflare Tunnel |
| [Свой VPS](#свой-vps-две-команды) | постоянный сервер для игры | VPS с Docker |
| [Свой домен и https](#свой-домен-и-https-постоянный-адрес) | нужен постоянный адрес `wss://` с сертификатом | домен + порты 80/443 или Cloudflare |
| [Хостинг ботов](#хостинг-ботов-вместо-vps-bothost-и-подобные) | своего VPS нет, есть аккаунт Botohost | аккаунт и приватный репозиторий (или готовый образ) |
| [Несколько регионов](CLUSTER.md) | игроки в разных странах, нужен выбор ближайшего сервера | directory + ноды, отдельный документ |

Дальше — [WebRTC-канал](#webrtc-канал-для-синка-объектов-udp-необязательно) для синка объектов по UDP (не
обязателен) и [переменные окружения](#переменные-окружения) со всеми настройками.

## Установщик: один скрипт

`install.sh` — установка на чистый Ubuntu/Debian VPS: сам ставит Docker, спрашивает, что это за сервер и
как к нему подключаться, поднимает всё через `docker compose` и печатает готовый адрес для плагина.

```bash
git clone https://github.com/EwenLoy/starkflow.git && cd starkflow
sudo bash install.sh
```

Скрипт спросит:

1. **Что ставим** — нода (игровой сервер) или `directory` (распределитель нескольких регионов, см.
   [CLUSTER.md](CLUSTER.md)).
2. **Как подключаться** — свой домен с https через Caddy, домен через Cloudflare Tunnel (порты открывать не
   нужно) или без домена (`http://IP:8080`).
3. **Домен** — скрипт сверит A-запись с IP сервера. Если домен за оранжевым прокси Cloudflare, он скажет сразу:
   Let's Encrypt не подтвердит домен через прокси, нужен `Proxy status = DNS only` (серое облако).
4. **WebRTC** — необязательный UDP-канал для синка объектов.

Без вопросов (для автоматизации):

```bash
sudo bash install.sh --domain game.example.com --yes
sudo bash install.sh --no-domain --yes
sudo bash install.sh --mode directory --domain dir.example.com --yes
sudo bash install.sh --token eyJhIjoi... --domain game.example.com --yes
```

После установки: `sudo bash install.sh --status`, `--logs`, `--update`, `--down`. `STARKFLOW_SECRET` скрипт
генерирует сам и при повторном запуске не меняет, поэтому токены игроков не слетают. Порты всё равно надо
открыть в фаерволе панели VPS: `80/tcp` и `443/tcp`+`443/udp` для варианта с Caddy, порт сервера — для варианта
без домена.

## Публичный сервер прямо со своего ПК (Windows, без Docker)

Один скрипт: собирает сервер, запускает его на `localhost`, поднимает Cloudflare Tunnel и печатает готовый адрес.

```powershell
powershell -ExecutionPolicy Bypass -File tools/run-public.ps1
```

Что он делает:

- собирает `dist/starkflow.exe` через `go build` (флаг `-NoBuild`, если бинарник уже собран);
- при первом запуске генерирует `STARKFLOW_SECRET` и сохраняет его в `.env`, чтобы токены игроков не слетали
  после перезапуска сервера;
- поднимает сервер на `http://localhost:8080` (`-Port 9000` — если нужен другой порт) и ждёт ответа `/health`;
- скачивает `tools/bin/cloudflared.exe`, если `cloudflared` не найден в `PATH` (Docker и аккаунт Cloudflare не нужны);
- печатает два адреса: публичную страницу `https://xxxx.trycloudflare.com` и адрес для плагина C3
  `wss://xxxx.trycloudflare.com/ws`.

Из C3 на https-странице (`preview.construct.net`, itch.io, GitHub Pages) нужен именно `wss://`: адрес туннеля
публичный, поэтому браузер не считает соединение локальным и не блокирует его. Логи обоих процессов лежат в
`dist/logs/` (`server.log`, `server.err.log`, `tunnel.log`, `tunnel.err.log`). Окно скрипта закрывать нельзя:
Ctrl+C останавливает и туннель, и сервер, ПК должен оставаться включённым.

Адрес `trycloudflare` выдаётся на каждый запуск новый. Постоянный адрес (`wss://game.example.com/ws`) — туннель
по токену из Cloudflare Zero Trust → Networks → Tunnels:

```powershell
powershell -ExecutionPolicy Bypass -File tools/run-public.ps1 -TunnelToken eyJhIjoi...
```

Проверка: `curl https://xxxx.trycloudflare.com/health` отвечает `ok`, а живой smoke-тест через туннель —
`SF_WS=wss://xxxx.trycloudflare.com/ws node tests/server-smoke.mjs` (нужен Node 22+).

Без скрипта то же самое вручную: `cloudflared tunnel --url http://localhost:8080`, в свойствах плагина —
`wss://<адрес туннеля>/ws`.


## Свой VPS: две команды

Подходит для маленького VPS (серверу хватает 64–128 МБ), где из инструментов есть только Docker.
В репозитории лежат `Dockerfile` (сборка Go → маленький Alpine, запуск от непривилегированного пользователя)
и `docker-compose.yml`.

```bash
git clone https://github.com/EwenLoy/starkflow.git
cd starkflow
# открой docker-compose.yml и задай свой STARKFLOW_SECRET — иначе после перезапуска сервера токены игроков слетают
docker compose up -d --build
docker compose logs -f starkflow        # видно строку "StarkFlow listening addr=:8080"
```

Друг открывает `http://<IP-сервера>:8080` — это встроенный тестовый клиент (лобби, комнаты, бой с боссом,
синхронизация курсоров). Порт 8080 нужно открыть в панели VPS или в фаерволе.

**Если игра в C3 открыта у друга по https** (itch.io, GitHub Pages, свой домен) — нужен `wss://`, иначе браузер
заблокирует соединение. Самый простой путь без открытия портов — туннель, он уже описан в том же compose-файле:

```bash
docker compose --profile tunnel up -d
docker compose logs tunnel | grep trycloudflare     # получишь адрес вида https://xxxx.trycloudflare.com
```

В свойствах плагина тогда указывай `wss://xxxx.trycloudflare.com/ws`. Туннель `trycloudflare` — тестовый: адрес
меняется после каждого перезапуска контейнера. Для постоянного адреса на своём домене есть отдельный
`docker-compose.tls.yml` — см. следующий раздел.

Проверки: образ собирается и проверяется в CI (job `docker`: сборка, запуск, ожидание `/health`, затем smoke-тест
внутри контейнера), а состояние контейнера видно через `docker compose ps` — healthcheck стучит в `/health`.


## Свой домен и https (постоянный адрес)

`docker-compose.tls.yml` даёт `wss://` на твоём домене двумя способами. Оба читают `.env`: скопируй
`.env.example` в `.env` и заполни `STARKFLOW_SECRET` и `SF_DOMAIN`.

**Вариант 1 — Caddy на том же сервере.** Нужны открытые порты 80 и 443 и A-запись домена на IP сервера:

```bash
cp .env.example .env     # STARKFLOW_SECRET и SF_DOMAIN=game.example.com
docker compose -f docker-compose.tls.yml --profile caddy up -d --build
docker compose -f docker-compose.tls.yml logs -f caddy   # здесь видно, что сертификат получен
```

Caddy сам получает и продлевает сертификат Let's Encrypt и сам проксирует WebSocket — весь конфиг это файл
`Caddyfile`. Адрес для плагина C3: `wss://game.example.com/ws`. Проверка: открой `https://game.example.com`,
страница сама подставит `wss://` и покажет «подключено».

**Вариант 2 — туннель Cloudflare, порты можно вообще не открывать.** В Cloudflare Zero Trust → Networks →
Tunnels создай туннель, добавь публичный хостнейм `game.example.com` → `http://starkflow:8080` и скопируй токен:

```bash
CF_TUNNEL_TOKEN=eyJhIjoi... docker compose -f docker-compose.tls.yml --profile cfdomain up -d --build
```

DNS-запись и сертификат Cloudflare сделает сам. Адрес для плагина тот же: `wss://game.example.com/ws`.

Оба файла проверяются в CI командой `docker compose config -q`, так что синтаксис и переменные заведомо валидны.

Если домен на Cloudflare и включён оранжевый прокси, для варианта 1 поставь SSL-режим **Full (strict)**: иначе
получится петля редиректов между Cloudflare и Caddy.

**Если сертификат не выпускается.** В логах (`docker compose -f docker-compose.tls.yml logs caddy`) видно
`challenge failed ... Cannot negotiate ALPN protocol "acme-tls/1"` и следом неудачный `http-01` — значит до сервера
доходит не Let's Encrypt, а прокси Cloudflare. Проверка **на самом сервере** (снаружи DNS может подменяться
провайдером): `getent ahostsv4 game.example.com` должен вернуть IP этого VPS, а не `104.*`, `172.67.*` или
`188.114.*`. Что делать: у записи A в Cloudflare выставить `Proxy status = DNS only` (серое облако) — явная запись
перекрывает wildcard `*`, из-за которого любой субдомен тоже уходит в прокси; либо оставить прокси и перейти на
туннель (`--profile cfdomain`). После правки DNS: `docker restart starkflow-caddy-1` — Caddy сбросит бэкофф и сразу
пойдёт за сертификатом в production CA (staging-сертификат браузер не примет). Признак успеха в логе —
`certificate obtained successfully` с `issuer: acme-v02.api.letsencrypt.org-directory`.


## Хостинг ботов вместо VPS (Bothost и подобные)

Такие платформы сделаны под Telegram-ботов, но этому серверу подходят: он слушает `0.0.0.0`, длительное
соединение держится за счёт `ping` каждые 15 с (прокси не рвёт его по таймауту), а состояние нигде не хранится —
перезапуск контейнера означает лишь то, что игроки переподключатся по своим токенам.

- **Язык разработки** в форме — **Go**, не Python: при Python платформа собирает проект как Python-бота, ищет
  `requirements.txt`, не находит и падает с «Сборка Docker образа не была завершена успешно».
- **Dockerfile** уже лежит в корне репозитория: включи «Использовать собственный Dockerfile». Без галочки
  платформа сгенерирует Dockerfile под выбранный язык и наш вообще не прочитает.
- **Если панель считает корнем проекта папку `server/`** (Orkestr и подобные: у них есть поле «каталог» или они
  определяют Go-модуль по `go.mod`), она ищет `Dockerfile` рядом с `go.mod` и, не найдя, генерирует свой —
  ожидающий `main.go` в корне. Сборка тогда падает на `no Go files in /app`: в `server/` в корне `.go`-файлов
  нет, точка входа лежит в `server/cmd/starkflow`. Для такого случая в репозитории есть второй файл,
  `server/Dockerfile`: он собирает `./cmd/starkflow` и не требует никаких полей в панели. Разница с корневым —
  в нём нет `cloudflared`/`entrypoint.sh`, поэтому туннель поднимай на стороне платформы или используй корневой
  Dockerfile (корень репозитория как контекст).
- **Главный файл** оставь пустым: со своим Dockerfile команду запуска задаёт `ENTRYPOINT ["/usr/local/bin/starkflow"]`,
  а поле «Главный файл» влияет только на автогенерацию Dockerfile.
- **`Dockerfile` — только ASCII или UTF-8 без BOM и без кириллических комментариев.** Иначе лог сборки
  обрывается сразу после `Cloning into...`, бот уходит в `failed`, и в панели нет никакой ошибки: комментарии в
  этом файле переведены на английский именно поэтому.
- **Приватный репозиторий**: в Git URL нужен токен доступа — `https://<логин>:<PAT>@github.com/EwenLoy/starkflow.git`,
  иначе клонирование не пройдёт и до сборки дело не дойдёт.
- **Свой домен вместо поддомена `*.bothost.tech`**, два пути. Официальный: запросить у поддержки Botohost IP для
  DNS-записи (в их доке так и написано — «настройте запись на IP, который выдаст поддержка»). Без поддержки:
  туннель Cloudflare прямо в контейнере. В Cloudflare Zero Trust → Networks → Tunnels создай туннель, добавь
  публичный хостнейм `game.example.com` → сервис `http://localhost:3000` (это внутренний порт бота из панели),
  скопируй токен и положи его в переменную `CF_TUNNEL_TOKEN`, затем сделай новый деплой. Домен, сертификат и
  `wss://` при этом целиком на стороне Cloudflare, Botohost в схеме не участвует; адрес для плагина C3:
  `wss://game.example.com/ws`.
- **Как прикрепить свой домен в панели**: поле «Кастомный домен» принимает только поддомены `bothost.tech` и
  `test.bothost.tech`, внешний домен туда не вписать — его подключают через поддержку. Шаблон тикета: «Бот
  `bot_<id>`. Прошу подключить мой домен `game.example.com`: нужен IP (или CNAME-цель) для DNS-записи и маршрут на
  мой контейнер, сертификат на `game.example.com`.» Дальше в Cloudflare: A-запись `game.example.com` → выданный IP,
  **проксирование выключено (серая тучка)**, пока Botohost не выпустит Let's Encrypt; после проверки оранжевую тучку
  можно включить и поставить SSL-режим **Full (strict)**.
- **Несколько нод в разных регионах** (ближайший выбирает клиент, как в Photon): один бот-распределитель
  (`STARKFLOW_MODE=directory`) + по боту на регион (`STARKFLOW_REGION=eu`, `ru`, …). В плагине Server URL —
  адрес распределителя (`https://dir.example.com`), свойство **Connection mode** можно оставить Auto. Каждому
  боту-ноде свой поддомен (`eu.example.com`), `STARKFLOW_PUBLIC_URL=wss://eu.example.com/ws` и тот же
  `STARKFLOW_CLUSTER_SECRET`. Подробности и порядок проверки — `docs/CLUSTER.md`.
- **Если домен отдаёт 404**, это ответ не сервера, а шлюза платформы (`curl` показывает Go-шный
  `404 page not found` с `Content-Type: text/plain` и без заголовка `Server`; наш сервер на `/health` отдаёт
  `ok`, а на `/` — страницу). Значит маршрут «домен → контейнер» не поднят: проверь галочку «Использовать домен»,
  совпадение порта в панели и `PORT` внутри контейнера, и сделай **повторный деплой** после смены домена или порта
  (в логах работы должна быть строка `StarkFlow listening addr=:3000`). Веб-интерфейс и домены на Botohost — только
  на платных тарифах; на бесплатном остаётся путь с туннелем Cloudflare, он от их домен-сервиса не зависит.
  Проверка наверняка: точно такой же 404 отдаёт **несуществующий** домен (`bot-0000000000-0000-nosuchbot.bothost.tech`),
  то есть имя в карточке бота — только зарезервированное, маршрута на шлюзе нет. Тогда помогает только повторный
  деплой, а дальше — поддержка («домен отдаёт 404 от шлюза, контейнер при этом жив и слушает PORT»). Смена любой
  переменной окружения на Botohost тоже применяется только новым деплоем — после такого деплоя маршрут и поднимается.
- Для браузера и плагина C3 включи опцию «Использовать домен» — на платных тарифах платформа выдаст
  `https://bot-<id>.bothost.tech` со своим сертификатом. Проверка, что через их прокси проходит WebSocket: страница
  по этому адресу должна показать «подключено».
- **Порт**: платформа передаёт порт в переменной `PORT` и требует слушать `0.0.0.0` — сервер делает это сам,
  поле «Порт» в панели можно не менять, `STARKFLOW_ADDR` задавать не нужно.
- **Домен и https**: включи «Включить веб-интерфейс / админку / webhook» — платформа выдаст адрес и сертификат
  (на бесплатном тарифе недоступно, на Базовом доступно). Свой домен тоже можно. Открой выданный адрес в
  браузере: страница подставит `wss://` сама, и если статус «подключено» — WebSocket через их прокси проходит.
- **Переменные окружения** (в панели): `STARKFLOW_SECRET` — обязательно, иначе токены игроков слетают при каждом
  перезапуске контейнера; при желании `STARKFLOW_ORIGINS=https://твой-домен` и `STARKFLOW_ROOM_NAME_MAX`.
- **Память**: серверу хватает 64–128 МБ. Если на тарифе мало памяти даже для сборки — собери образ локально и
  залей готовый: `docker save starkflow | gzip > starkflow.tgz`, на платформе `docker load`.

Проксирование WebSocket через домен Botohost проверено на живом боте: полный smoke-тест проходит через `wss://`.
Команда для проверки снаружи (Node 22+):

```powershell
$env:SF_BASE='https://bot-<id>.bothost.tech'; $env:SF_WS='wss://bot-<id>.bothost.tech/ws'; node tests/server-smoke.mjs
```
Ожидаемый результат — `Итого: 75 ok, 0 FAIL`. Если апгрейд всё же не проходит, остаются VPS (`docker-compose.yml`)
или вариант 2 из предыдущего раздела (туннель внутри контейнера).

## WebRTC-канал для синка объектов (UDP, необязательно)

Снимки объектов (`sync`) могут идти не по WebSocket (TCP), а по WebRTC DataChannel без повторов и без порядка — как UDP в шутерах: потерянный пакет просто пропускается и не задерживает следующие. Всё остальное (стейт, события, вход в комнаты) остаётся на WebSocket.

Включается одной переменной `STARKFLOW_RTC_PORT` — один UDP-порт на всех клиентов. Нужно:

1. **Открыть этот UDP-порт** в фаерволе (и пробросить в Docker: `- "40000:40000/udp"` в `docker-compose.yml`).
2. **В Docker и за NAT задать `STARKFLOW_RTC_PUBLIC_IP`** — внешний IP сервера. Без него сервер предложит клиенту свой внутренний адрес, и канал не поднимется. На VPS с публичным IP прямо на интерфейсе можно не задавать.
3. Туннель Cloudflare и обычные хостинги ботов UDP **не пропускают**: там канал не поднимется. Это не ломает игру — плагин через 3 с сам остаётся на WebSocket. Проверить, работает ли канал: в консоли браузера строка `[StarkFlow] sync goes over WebRTC`, подробности в `chrome://webrtc-internals`.

Если порт не задан, `welcome` не содержит `rtc`, и клиенты ведут себя ровно как раньше. Протокол — в `docs/PROTOCOL.md` (раздел `rtc.*`).

## Переменные окружения

- `STARKFLOW_ADDR`: адрес, по умолчанию `:8080`
- `PORT`: порт от хостинг-платформы (Bothost и подобные передают его сами). Используется, только если `STARKFLOW_ADDR` не задан, и приложение всё равно слушает `0.0.0.0`
- `STARKFLOW_SECRET`: секрет подписи токенов игроков. Если не задан, при каждом запуске берётся случайный, и токены старых игроков перестают работать (плагин сам получит новый)
- `STARKFLOW_ORIGINS`: разрешённые Origin через запятую. Пусто = разрешено всё (только для разработки)
- `STARKFLOW_ROOM_NAME_MAX`: максимальная длина названия комнаты в символах (любой язык, включая эмодзи), по умолчанию `32`. Лимит приходит клиенту в `welcome`
- `STARKFLOW_BATCH_MS`: окно батчинга рассылки в мс, по умолчанию `40`; `0` — выключить (кадр на каждое изменение). `welcome` сообщает его клиенту как `batchMs`. Окно действует на `state.changed`, `player.props` и `ok`; снимки объектного синка (`sync`) и остальные сообщения идут сразу, поэтому в задержку показа они это окно не добавляют (`welcome.syncNow`). Для быстрых игр (экшен) ставьте `8..16` — это задержка свойств и стейта. Для пошаговых и чатов подходит и `40`
- `STARKFLOW_SUSPEND_TTL`: сколько секунд сервер держит место за игроком с оборванной связью, по умолчанию `30`; `0` — удалять сразу (остальные получают `player.left` в момент обрыва). Комната может переопределить это для себя полем `room.join.suspendTTL` (действие «Set player timeout» в плагине), но не больше 5 минут
- `STARKFLOW_SYNC_BYTES_PER_SEC`: бюджет канала `sync` в байтах в секунду на игрока, по умолчанию `524288` (512 КБ/с); `0` — без ограничения. Ограничивает, сколько игрок может рассылать снимков объектов всем остальным
- `STARKFLOW_MAX_PLAYER_PROPS`, `STARKFLOW_MAX_STRING_BYTES`, `STARKFLOW_MAX_MSG_BYTES`, `STARKFLOW_MAX_SYNC_BYTES`: лимиты `player.set` и кадра/снимка. `MAX_MSG_BYTES` — это лимит принимаемого кадра, он приходит клиенту как `maxMsg`, и плагин держит свои батчи ниже него
- `STARKFLOW_RTC_PORT`: UDP-порт WebRTC-канала для `sync`. Не задан — WebRTC выключен (см. раздел выше)
- `STARKFLOW_RTC_PUBLIC_IP`: внешний IP сервера для ICE (через запятую), обязателен в Docker и за NAT
- `STARKFLOW_RTC_ICE`: STUN-серверы, которые клиент получает в `welcome` (через запятую), по умолчанию `stun:stun.l.google.com:19302`; `none` — пустой список
- `CF_TUNNEL_TOKEN`: токен туннеля Cloudflare. Если задан, контейнер вместе с сервером поднимает `cloudflared` и отдаёт игру на своём домене с https/`wss` (публичный хостнейм и сервис `http://localhost:PORT` настраиваются в дашборде Cloudflare). Не задан — контейнер запускает только сервер

Остальные лимиты лежат в `server/internal/config/config.go`.
