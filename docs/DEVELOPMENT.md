## Запуск сервера локально

Нужен Go 1.22 или новее.

```bash
cd server
go mod tidy          # скачает gorilla/websocket и создаст go.sum
go test ./...        # тесты стейта и токенов
go run ./cmd/starkflow
```

## Встроенный тестовый клиент

Открой `http://localhost:8080` — это встроенный тестовый клиент, полный пример всего, что умеет сервер.

**Подключение.** Впиши имя, нажми «Подключиться» (адрес и App ID подставляются автоматически). Справа видны
вы, ваш токен и статус; там же кнопки «Отключиться», «Забыть токен» и галка авто-возврата в комнату после обрыва.

**Комнаты.** После подключения подгружается список комнат вашего App ID — у каждой видно имя и `#id`. «Войти»
подключает к выбранной комнате (по id), «Войти в случайную» — к любой свободной.

- Имя комнаты — просто метка: **любой язык, до 32 символов** (лимит задаёт сервер и присылает в `welcome`).
- Каждая кнопка «Создать комнату» создаёт **новую** комнату со своим id — одинаковые имена разрешены.

**Режимы.**

| Режим | Что происходит |
|---|---|
| Бой с боссом | общий HP: «Ударить −10» любого игрока меняет его у всех (HP-бар); «Попытка set boss_hp» должна вернуть ошибку 402 |
| Синхронизация курсоров | веди мышь по полю: остальные видят твой курсор с ником и цветом, клик по полю даёт у остальных вспышку (это событие) |

Режим хранится в стейте комнаты ключом `mode`, поэтому вошедший в существующую комнату подхватывает его
автоматически. Сами позиции идут **стейтом игрока** (`player.set "cursor"`), а не общим стейтом комнаты:
перезаписать чужой курсор нельзя, ключи не тратят лимит комнаты, а вышедший игрок уносит свой курсор с собой —
призраков не остаётся.

**Настройки режима курсоров** (обе запоминаются в `localStorage`):

- **«Частота отправки позиции»** — 1–60 кадров/с (по умолчанию 20) — сколько кадров уходит в сеть. 60 — это
  ровно потолок сервера (60 сообщений/с на соединение); интервал отправки округляется вверх (17 мс вместо
  16.67 мс), поэтому фактически получается ~58 кадров/с, зато без ошибок 500. Отправка идёт фиксированным
  тактом, так что заданная частота соблюдается точно (проверено: 10 → 12 кадров за 1.2 с, 20 → 24, 40 → 48,
  60 → 70).
- **«Сглаживание чужого курсора»** — 0–500 мс вручную, либо галка «авто от частоты» (авто = 1.4 × интервал
  отправки, зажато в 70…300 мс). `0` — сглаживания нет, чужой курсор двигается рывками с частотой отправки;
  больше миллисекунд — плавнее, но с задержкой. Частота отвечает за трафик, сглаживание — за вид.

**Игра вдвоём.** Открой страницу **во втором браузере или в приватном окне**: вкладки одного браузера делят
токен в `localStorage` и играют за одного игрока (сервер считает это возвратом того же игрока и закрывает
старое соединение).

> [!NOTE]
> Страница вшита в бинарник сервера (`//go:embed web/index.html`), поэтому после её правки сервер надо
> перезапустить: иначе он продолжит отдавать старую версию, и в браузере будет не то, что лежит в
> `server/internal/server/web/index.html`.


## Сборка аддона

`dist/starkflow.c3addon` — это zip, в корне которого лежит `addon.json`. Собирать заново после любой правки в `plugin/`:

```powershell
powershell -ExecutionPolicy Bypass -File tools/build-addon.ps1
```

В C3 после пересборки аддон надо переустановить: View → Addon Manager → Install new addon. Если плагин уже стоял,
старую версию лучше удалить, иначе C3 может держать её в кэше.


## Тесты

```bash
cd server && go test ./...          # unit-тесты: стейт (лимиты, режимы ключей) и токены
node tests/plugin-mock-test.js      # плагин: сверка ACE и поведение на заглушке WebSocket
```

Живой end-to-end тест против запущенного сервера (нужен Node 22+ со встроенным `WebSocket`):

```powershell
cd server && go build -o starkflow.exe ./cmd/starkflow
$env:STARKFLOW_SECRET='devsecret'; ./starkflow.exe    # отдельное окно
node tests/server-smoke.mjs                            # 75 проверок протокола (SF_BATCHED=0, если сервер запущен с STARKFLOW_BATCH_MS=0)
```

Он проверяет вручную то, что не покрыто unit-тестами: `welcome`, создание комнаты и `room.joined`,
`state.add` с рассылкой обоим игрокам, ошибки 100/102/200/300/303/400/402/403, зажим по `min`,
`toggle`, события `to: all/others`, `player.props`, `player.suspended` и повторный вход по токену,
`ping/pong`, `room.list` и изоляцию по `app`. Переменные `SF_BASE` и `SF_WS` переопределяют адрес.

| Часть | Статус |

| Плагин (рантайм), 132 ACE (35 действий, 32 условия, 65 выражений) | Проверен тестом на заглушке WebSocket (`node tests/plugin-mock-test.js`): подключение, комната, события, стейт, реконнект с автоматическим повторным входом, ошибки, батчинг и канал `sync` с интерполяцией; режим подключения (нода/распределитель) и выбор ближайшего региона |
| Сверка `aces.json`, языкового файла и кода | Проверена скриптом: каждое ACE есть в коде с нужным числом параметров |
| Тестовая страница сервера | Проверена в реальном браузере (headless Chrome через DevTools Protocol): 40 проверок отрисовки курсоров, настроек частоты и сглаживания |
| **Сервер на Go** | Собран и прогнан на Go 1.26.1: `go mod tidy`, `go build ./...`, `go vet ./...`, `go test ./...` — без ошибок и правок; плюс живой smoke-тест `node tests/server-smoke.mjs` (75 проверок, включая batch) против запущенного сервера — всё зелёное |
| **Кластер (directory + ноды)** | Проверен юнит-тестами `server/internal/directory`: CORS-preflight для страницы игры, список регионов (`/regions`), выбор ноды по региону и по нагрузке, аффинити комнаты важнее региона, билет привязан к App ID. Плюс живой сквозной тест `node tests/cluster-e2e.mjs` против запущенных директора и двух нод в разных регионах: preflight, `/regions`, `assign` по региону, приём билета нодой, комната важнее региона (по id и по имени) и вход второго клиента в ту же комнату |
| **Загрузка плагина в Construct 3** | **Не проверялась**: формат файлов сверен с документацией Addon SDK v2, но в самом C3 его не запускали |


## Отличия от плана в документе

- Возврат в комнату после обрыва идёт по подписанному `userId`, а не по отдельному `resumeKey`: токен уже подписан, второй ключ не нужен.
- Не сделано: режимы комнат locked и allowlist, шаблоны, админ-API, `appId` с отдельными секретами, `redirect` и Redis (это M5-M8). Задел есть: ключ комнаты уже `appId:имя`.
- `Shutdown` сервера пока не закрывает открытые WebSocket-соединения аккуратно.
