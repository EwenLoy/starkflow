# Протокол StarkFlow

Схема сообщений в коде: `server/internal/proto/proto.go`. Ниже то, что нужно знать для игры.



URL: `ws(s)://host/ws?v=1&app=APPID`. Все кадры JSON с полем `t`.

Комната живёт по **id** (8 hex-символов, генерирует сервер), а имя — просто метка для людей:
в `room.join` поле `room` — это либо id, либо имя; `create: true` **всегда** создаёт новую комнату
(одинаковые имена разрешены), `create: false` ищет сначала по id, потом по имени (самую старую
комнату с таким именем). `room.joined` отдаёт `roomId`, `room.list` — массив
`{id, room, players, maxPlayers, locked}`, `welcome` — `roomNameMax`. Имена пишутся на любом языке;
управляющие символы вырезаются, длина считается в символах (не в байтах).

Закрытые комнаты: в `room.join` можно передать `password`. Сервер хранит только хэш (SHA-256 с солью комнаты),
в списке такая комната помечена `locked: true`, а неверный или отсутствующий пароль даёт ошибку **307**.
Игрок, который возвращается с тем же userId (по своему токену), входит в закрытую комнату **без** пароля:
это возврат в свою комнату, а не новый вход.

Обрыв связи: по умолчанию сервер держит место за игроком, у которого пропала связь, 30 секунд
(остальные получают `player.suspended`, потом `player.left` с `reason: "timeout"`). Поле `room.join.suspendTTL`
меняет это для создаваемой комнаты: секунды, `0` — удалять сразу, как при `room.leave` (тогда `player.left`
с `reason: "left"` приходит в момент обрыва, а `player.suspended` не приходит вовсе). `room.joined` возвращает
`suspendTTL` комнаты, серверное значение по умолчанию задаёт `STARKFLOW_SUSPEND_TTL`.

- Клиент: `hello`, `room.join`, `room.leave`, `room.list`, `event`, `state.set`, `state.add`, `state.toggle`, `player.set`, `ping`, `batch`, `sync`
- Сервер: `welcome`, `room.joined`, `player.joined`, `player.left`, `player.suspended`, `player.resumed`, `player.props`, `host.changed`, `event`, `state.changed`, `room.list.result`, `ok`, `err`, `pong`, `batch`, `sync`

`batch` — несколько сообщений одним WebSocket-кадром: `{"t":"batch","items":[...]}`, каждый элемент `items` — обычное сообщение того же направления, порядок сохраняется. `welcome` сообщает `batch: true` (сервер понимает и шлёт `batch`), `maxString` и `maxPlayerProps` (лимиты `player.set`), `maxMsg` (лимит кадра, который сервер принимает, — клиент держит батчи ниже него), `sync: true`, `maxSync` и `batchMs` (см. ниже).
- От клиента: до 64 элементов, `hello` и вложенный `batch` внутри запрещены (ошибка **101** на этот элемент), больше 64 — **501**. Каждый элемент тратит токен лимита частоты как обычное сообщение (кадр оплачивает первый): батч экономит кадры, а не лимит. Когда лимит исчерпан, остаток батча отбрасывается с **одной** ошибкой **500** (а не с ошибкой на каждый элемент).
- От сервера: `state.changed`, `player.props` и `ok` копятся отдельно для каждого получателя и уходят одним кадром раз в `STARKFLOW_BATCH_MS` (по умолчанию 40 мс; `0` — без батчинга, кадр на каждое сообщение). Из нескольких `player.props` одного игрока с одним ключом за это окно уходит только последнее. Если накопленное не влезает в `maxMsg`, батч режется на несколько кадров. Остальные сообщения (`event`, `player.joined`/`left`, `err`, …) идут сразу, но уже накопленное для этого получателя уходит перед ними в том же кадре, так что порядок не меняется.

Правила ключей стейта (`schema` при создании комнаты): `kind` (num, str, bool), `mode` (set, add, const, once, server), `min`, `max`, `maxDelta`, `reject`, `maxLen`.

Два разных хранилища, не путать:
- `state.set/add/toggle` — **общий стейт комнаты** (ключи + правила из `schema`): писать может любой игрок в комнате, `state.changed` рассылается всем, включая автора, лимит — 20 записей/с на игрока, 64 ключа и 64 КБ на комнату. Сюда идут `boss_hp` и маркер режима `mode`.
- `player.set` — **стейт игрока** (`player.props`): писать может только сам игрок, значение приходит как `player.props`, а вошедшему — внутри `players[].props` в `room.joined`. До `STARKFLOW_MAX_PLAYER_PROPS` ключей на игрока (по умолчанию 24) и `STARKFLOW_MAX_STRING_BYTES` байт на строку (по умолчанию 4096), правил ключей нет, отдельного лимита на частоту нет (только общий лимит 60 сообщений/с на соединение, элемент `batch` считается за сообщение). Здесь лежат позиции курсоров, а на старом сервере (без канала `sync`) — ещё и чанки объектного синка `_sf0…_sf7`.

`sync` — снимок синкаемых объектов игрока (канал объектного синка). Клиент: `{"t":"sync","seq":N,"ts":мс,"iv":мс,"objs":[[slot,flags,...],...]}` — `seq` растёт с каждым снимком, `ts` — часы отправителя в мс (сверять с другими не нужно, получатель смотрит только на разницу между снимками), `iv` — интервал отправки, `objs` — массив записей объектов (формат записи — как в `_sf`-чанках, см. docs/GAME-GUIDE.md). Сервер содержимое не разбирает: проверяет, что `objs` — массив (иначе **401**), не больше `maxSync` байт (`STARKFLOW_MAX_SYNC_BYTES`, по умолчанию 32 КБ, иначе **404**) и что игрок не превысил бюджет канала `STARKFLOW_SYNC_BYTES_PER_SEC` байт/с (по умолчанию 512 КБ, `0` — без ограничения; иначе **500**), и пересылает остальным как `{"t":"sync","id":игрок,"seq","ts","iv","objs"}` через батчинг (без склейки: для интерполяции нужен каждый снимок). Снимок уходит всем остальным, поэтому и лимит байтовый, а не счётный. Пустой `objs: []` бюджетом не ограничивается: он весит почти ничего, а без него у остальных навсегда остались бы копии объектов. Последний непустой снимок игрока хранится и приходит вошедшим в `players[].sync`; пустой `objs: []` означает «объектов больше нет» и стирает его.

`rtc.*` — WebRTC-канал для `sync` (этап 4). Включается на сервере переменной `STARKFLOW_RTC_PORT` (см. docs/DEPLOY.md); тогда `welcome` содержит `rtc: true` и `iceServers: [...]` (формат `RTCIceServer`, из `STARKFLOW_RTC_ICE`; без поля клиент берёт `stun:stun.l.google.com:19302`). Без порта `rtc` в `welcome` нет, и `rtc.offer` получает ошибку **101**. Клиент шлёт `rtc` только если в `welcome` есть и `rtc: true`, и `sync: true`; старому серверу ничего нового не приходит. Предлагает соединение всегда клиент, сервер только отвечает. Всё идёт по уже открытому WebSocket:
- клиент → `{"t":"rtc.offer","sdp":"..."}`, сервер → `{"t":"rtc.answer","sdp":"..."}`;
- `{"t":"rtc.ice","candidate":{candidate,sdpMid,sdpMLineIndex,usernameFragment}}` — trickle ICE в обе стороны; кандидаты, пришедшие до `rtc.answer`, клиент придерживает;
- `{"t":"rtc.close"}` в обе стороны — «эту сторону закрыли, шли `sync` по WebSocket».

Канал один, его создаёт клиент: DataChannel `"sync"`, `ordered: false`, `maxRetransmits: 0`. Сообщения в нём — текстовые JSON, ровно те же `sync`, что и по WebSocket (клиент → `{"t":"sync","seq","ts","iv","objs"}`, сервер → с `id`); сервер может прислать и `batch` из одних `sync`. Всё, что не `sync`, клиент из канала игнорирует. Проверки и лимиты сервер применяет те же, что для `sync` по WebSocket, но ошибку шлёт по WebSocket.

Поведение клиента: канал не открылся за 3 с — `rtc.close`, до перезагрузки страницы WebRTC больше не пробует. Канал упал после открытия — `rtc.close`, `sync` снова идёт по WebSocket, при следующем реконнекте попытка будет снова. Пустой `objs: []` всегда идёт по WebSocket (его потеря оставила бы копии объектов). Если в канале скопилось больше 64 КБ или снимок больше `maxMessageSize`, этот снимок уходит по WebSocket. В worker-режиме Construct `RTCPeerConnection` нет — остаётся WebSocket.

Что делает сервер (`server/internal/rtc`, `server/internal/server/client.go`, `Room.Sync`): один UDP-порт на всех (ICE UDP mux), на соединение не больше 4 `rtc.offer` (иначе **500**), offer до 16 КБ; канал, не открывшийся за 15 с, закрывается; из канала принимается только `sync` и не чаще общего лимита сообщений (лишнее молча отбрасывается). Подробно:
- на каждого получателя — `sync` либо в его открытый DataChannel, либо в WebSocket-батч, **не в оба**;
- пакеты по UDP приходят не по порядку: снимок с `seq` не больше последнего принятого от этого игрока **не сохранять** как «последний» для вошедших (иначе устаревший снимок, пришедший после пустого `objs: []`, оживит копии объектов). Счётчик сбрасывать, когда игрок заново подключился (resume после перезагрузки страницы начинает `seq` с 1). Переслать опоздавший можно — клиент сам отбрасывает опоздавшие (`seq` в пределах 64 и `ts` в пределах 2 с от новейшего), а снимок с меньшим `seq`, но с более поздним `ts`, считает перезапуском отправителя;
- закрывать `RTCPeerConnection` при `rtc.close`, при закрытии WebSocket и если канал не открылся за разумное время.
